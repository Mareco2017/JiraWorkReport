# 批量填报失败：模型服务数据去向尚未核实

- 日期：2026-11-13
- 现象：批量填报「手动粘贴」4 行工时后点击「开始解析」，报错
  `模型服务的数据去向尚未核实，请先完成模型服务配置。当前内容已保留。`（`code = DESTINATION_UNVERIFIED`）
- 本轮范围：**只做原因分析与方案设计，未改动任何代码**

---

## 1. 结论

**与 JIRA、网络、API Token、模型服务本身都无关。** 这个错误在调用模型之前就被抛出，原因是：

> 当前这份 Windows 打包产物里，`site-defaults` 的 `trustedModelOrigins` 是空数组，而 `approvedInternal` 只能由这个名单授权。设置页每次「检测并保存」都会按空名单重算，把 `approvedInternal` 写回 `false`，于是批量解析在发送内容前被拒绝。

一句话：**这是一项安全闸门（防止真实工作内容被发到未核实的模型地址），不是故障；缺的是构建期没有把内网模型网关写进可信来源。**

---

## 2. 根因链路（代码证据）

| 步骤 | 位置 | 行为 |
| --- | --- | --- |
| ① 启动读部署配置 | [app/main.js](../app/main.js) 第 18 行 | `loadSiteDefaults(directory)` |
| ② 校验并返回 | [app/site-defaults.js](../app/site-defaults.js) 第 8–24 行 | 优先读 `site-defaults.local.json`，不存在则回退 `site-defaults.example.json` |
| ③ 注入服务 | [app/main.js](../app/main.js) 第 33 行 | `trustedModelOrigins: siteDefaults.trustedModelOrigins` |
| ④ 检测模型服务 | [app/service.js](../app/service.js) 第 108–123 行 | `candidate.approvedInternal = (this.trustedModelOrigins \|\| []).includes(origin)` |
| ⑤ 保存 | [app/service.js](../app/service.js) 第 125–133 行 | 把 `candidate`（含 `approvedInternal`）整体写入 `settings.json` |
| ⑥ 批量解析 | [app/batch-import.js](../app/batch-import.js) 第 39–46 行 | `this.agent.extract(content, config.agent)` |
| ⑦ 闸门 | [app/agent.js](../app/agent.js) 第 38–43 行 | `if (config.mode !== 'custom' \|\| !config.approvedInternal) throw DESTINATION_UNVERIFIED` |

关键点：

- `trustedModelOrigins` 是**唯一**授权来源。源码注释写明「可信目的地来自主进程中已核实的单位网关，**页面字段无法自行授予权限**」——即界面上填什么地址都不会自动变成可信。
- 第 ⑦ 步的检查发生在 `run()`（真正启动 CLI）**之前**，所以报错时根本没有网络请求，也解释了为什么 JIRA 侧一切正常。
- 第 ⑤ 步会把结果持久化，所以「昨天还能用、今天不行」的典型成因就是中途又点过一次「检测 / 保存」。

## 4. 为什么「检测连接」能通过、「开始解析」却失败

这是本次最容易误判的地方：

- `agent.test()` 见 [app/agent.js](../app/agent.js) 第 23–27 行，**不检查** `approvedInternal`，因为检测只用虚构文本（`'整理一个虚构的需求分析示例'`），发送它没有风险。
- `agent.extract()` / `agent.suggest()` 才检查，因为它们要把**真实内容**发出去。

所以「检测通过」只证明 CLI 能跑、模型能回话，**不证明允许发送真实工作内容**。当前界面没有把「数据去向是否已核实」单独展示出来，用户只能到解析这一步才看到失败——这是体验缺陷，不是功能错误。

## 5. 影响范围

| 功能 | 是否受影响 | 原因 |
| --- | --- | --- |
| 批量填报 · 文件/粘贴解析 | ✅ 受影响 | `extract()` 闸门 |
| 批量填报 · 已完成待办载入 | ✅ 受影响（若默认值留空） | 走同一条 `batchImport` 通道，同样要求默认类型/耗时补齐前不依赖模型；但当前实现仍会调用 `extract` 之外的路径，需确认 |
| 按天填报的 AI 类型建议 | ⚠️ 潜在受影响 | `suggest()` 同样检查；当前渲染层未调用该命令，暂不体现 |
| 手工填报、JIRA 连接、提交工时、待办 | ❌ 不受影响 | 不经过 Agent |

> 说明：上表第二行中「已完成待办载入」是上一轮新增的功能，其默认值（类型/耗时）可留空、无需模型；但若实现里仍复用 `extract` 通道，则同样会被闸门挡住。这一条**待实施后再确认**。

## 6. 解决方案

### 方案 A（推荐，正规修复）：把内网网关写入可信来源并重新打包

新建 `app/site-defaults.local.json`：

```json
{
  "projectKey": "EXEPD",
  "trustedModelOrigins": ["https://sm-wenwen.exexm.com"],
  "notesRelativeDirectory": ""
}
```

然后重新打包：

```sh
npm install
npm run package:win
```

- 生效范围：分发给所有人的新包
- 代价：需要重新构建、重新分发
- 注意事项：
  1. 该文件被 `.gitignore` 忽略（不提交），但**会被打进包**——`scripts/package.mjs` 的 `ignore` 只排除 `docs/tests/dist/scripts`。
  2. 地址**不能带 `/v1`**。`site-defaults.js` 第 16–19 行要求 `url.origin === origin`，写成带路径会在启动时抛「站点配置格式不正确」，**应用直接起不来**。
  3. 数组必须是合法 JSON 数组，漏写会导致同样的启动失败。

### 方案 B（应急，不重新打包）：直接修正运行期开关

关闭应用，编辑 `%APPDATA%\jira-workbench\settings.json`：

```json
"agent": { "...": "...", "approvedInternal": true }
"modelServices": [{ "...": "...", "approvedInternal": true }]
```

- 生效范围：仅这一台机器、下一次「检测/保存」之前
- 优点：立即可用，无需重启打包流程
- 风险与约束：
  1. **任何一次在设置页点「检测连接」并「保存」，都会把它重置回 `false`**（第 ⑤ 步整体覆盖）。改完后不要再动 Agent 配置区。
  2. 这是**手动绕过安全闸门**。只有在确认 `sm-wenwen.exexm.com` 就是公司内网网关、且允许把工作内容发往该地址时才可使用。
  3. 不改变构建产物，换机/重装/清 userData 后失效。

### 方案 C（不可行）：改用「CLI 默认模型」

不成立。`extract()` 的要求是 `config.mode === 'custom' && config.approvedInternal`，`mode: 'default'` 同样被拒绝。默认模型指向何处无法在应用内核实，这正是闸门要防的场景。

### 方案 D（产品改进建议，后续迭代）

1. **设置页显式展示数据去向**：在「执行引擎 / 模型」卡片上增加一行「数据去向：已核实 / 未核实」，`approvedInternal=false` 时用警示色，而不是等解析时报错。
2. **错误文案给出可执行动作**：当前文案只说「请先完成模型服务配置」，但用户按提示去配置区也修不好。应补充：需要的 origin 字符串、这是构建期配置、以及「联系管理员 / 重新打包」的指引，并提供一个「复制 origin」按钮。
3. **保存时拦截**：在 `saveAgent` 返回前，若 `approvedInternal=false`，在界面上明确提示「已保存，但数据去向未核实，批量解析与 AI 建议将不可用」，避免用户误以为一切正常。
4. **降低改包依赖**：考虑由管理员在应用内首次确认可信来源（带审计记录），或在安装包里随 `projectKey` 一起声明，减少「每换一个网关就要重新打包」的运维成本。

### 10.6 评审：风险与不足（需知悉）

1. **重打包不会自动修复已持久化的开关**（最容易踩的坑）：`extract()` 读的是 `settings.json` 里的值，不会用新名单重算。必须在**新包**内重新「检测 + 保存」；若在**旧包**上点检测，反而会把值重置回 `false`。本文档已用运行期修正（10.1 第三行）临时消除这一步。
2. **信任被焊死在构建产物**：换网关、增减网关都要重新打包分发，应用内无运维手段。
3. **构建可重复性差**：`.local` 被 git 忽略，干净检出或 CI 会静默回落到示例（`DEMO` + 空名单），产出一个"看起来正常但发不出内容"的包。
4. **启动单点**：该文件任何语法/格式错误都会让 [app/main.js](../app/main.js) 第 18 行抛异常，应用**完全打不开**（不是降级）。本次已用 `loadSiteDefaults` 预校验规避，但这依赖流程而非代码保障。
5. **本次落地额外发现并修复了两个真实打包缺陷**：
   - 根目录旧构建目录 `JIRA工时填报-win32-x64/` 被递归打进 asar，使包从 8.9 MB 膨胀到 **391 MB**（内含嵌套 exe 与 locales）；
   - `Compress-Archive` 失败时只写非终止错误、进程仍返回 0，且丢失中文名 UTF-8 标记，导致 ZIP 静默缺失或解压乱码。
6. **未解决误导性提示**：设置页「检测」通过而「解析」失败的问题依旧存在（第 6 节方案 D）。
