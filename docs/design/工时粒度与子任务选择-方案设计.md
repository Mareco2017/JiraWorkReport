# 工时粒度 0.25h 与子任务手动选择 方案设计

- 文档状态：**已实施（2026-11-17）**
- 日期：2026-11-17
- 目标版本：0.2.1
- 涉及改造点：
  1. 工时最小粒度由 0.5h 调整为 **0.25h**
  2. 子任务未自动匹配时，可**不创建**，改为选择/输入一个**已存在的子任务**

> **范围说明（2026-11-17 补充）**：改造点 2 必须覆盖**批量填报**。批量页第 7 列当前是只读的"子任务映射结果"，且行上没有子任务候选数据，因此方案在 §3.6.2 单列一节，覆盖数据字段、取数方式（按需懒加载）、单元格交互、四处校验与清空规则；只改日填报无法闭环。

---

## 1. 结论摘要

| 改造点 | 改动性质 | 主要落点 | 风险 |
| --- | --- | --- | --- |
| 0.25h 粒度 | 规则常量 + 界面控件 + 文案 | `worklogs.js`、`todo-data.js`、`batch-import.js`、4 处 UI | 低；历史数据无需迁移，0.25 在二进制浮点中精确可表示 |
| 子任务手选 | 新增可选字段 + 提交解析分支 + **批量页单元格改造** | `worklogs.js`、`submission.js`、日填报 UI、**批量页 UI（`renderer.js`/`templates.js`/`styles.css`）**、历史展示 | 中；需保证"手选优先、否则自动创建"的语义不被绕过，且批量行换工单后不串单 |

不建议用一个开关全局关闭自动创建：**保留"默认自动创建"作为兜底**，只在用户明确选择了已有子任务时才走手选分支，避免把现有顺畅路径改坏。

### 2.2 设计

#### 2.2.1 规则常量集中

在 [app/worklogs.js](../../app/worklogs.js) 导出唯一来源：

```js
export const HOURS_MIN = 0.25;   // 15 分钟
export const HOURS_STEP = 0.25;
export const hoursValid = value => Number.isFinite(value) && value >= HOURS_MIN && Math.round(value / HOURS_STEP) * HOURS_STEP === value;
```

- [app/todo-data.js](../../app/todo-data.js) 与 [app/batch-import.js](../../app/batch-import.js) 改为 import 这两个常量，**不再各写一份**（这是本次最容易漏改的地方：三处规则目前是复制的）。
- 文案统一为「工时至少为 0.25 小时，且是 0.25 的倍数」。
- `seconds` 仍为 `Math.round(hours * 3600)`：0.25h = **900 秒**，整数无误差。

#### 2.2.2 精度说明（为什么这次不会引入小数误差）

0.25 = 2⁻²，可被二进制浮点精确表示，`0.25 + 0.5 + 1.25` 等累加不会出现 `0.30000000000000004` 这类问题。相比之下若选 0.1h 就会有误差，因此**不建议做成可配置粒度**。

#### 2.2.3 界面取值

**已确认：快捷块加入 `0.75`、`1.25`**，共 9 个：`0.25 / 0.5 / 0.75 / 1 / 1.25 / 1.5 / 2 / 2.5 / 3`。

| 控件 | 取值与排布 |
| --- | --- |
| 日填报快捷块 | 9 个；现有 `.hours-row .chip{flex:1}` 单行放不下（输入框固定 62px，剩余宽度每个不足 30px，`1.25` 会挤断），改为**两行 5 列网格**（第一行 `0.25~1.25`，第二行 `1.5~3`），输入框单独占位 |
| 批量工时浮层 `openBatchHours` | 9 个正好填满现有 `grid-template-columns:repeat(3,1fr)` → **3×3** |
| 待办完成对话框 | 9 个；`.worklog-chips` 已是 `flex-wrap`，自然换行，无需改布局 |
| 历史编辑浮层 `hourOptions` | 9 个，同上 3 列网格 |
| 数字输入 | `min="0.25" step="0.25"` |
| 批量页缺失提示 | `至少0.25h` / `0.25h倍数` |

> 布局注意事项记入实施清单：日填报需要改 [app/ui/styles.css](../../app/ui/styles.css) 的 `.hours-row`（`flex-wrap` 或 `grid`）与 [app/ui/templates.js](../../app/ui/templates.js) 的 chips 结构，否则新增两个块会把输入框挤变形。

#### 2.2.4 兼容性

- **历史数据**：既有 0.5/1.0 等记录全部仍然合法，无需迁移、无需重算。
- **待办**：已记录的 0.5h 工时不变；新记录可为 0.25。
- **Agent 识别**：提示词未约束步长，模型返回 1.25 过去会被标红，改造后成为合法值（这是本次改造的实际收益之一）。
- **Tempo/JIRA**：按秒写入，0.25h 无额外配置要求。

## 3. 改造点二：子任务支持手选已存在项

### 3.1 现状：找不到就创建，没有别的选择

[app/submission.js](../../app/submission.js) 第 222–246 行 `resolveTarget`：

```
父工单（需求故事 或 月度综合工时单）
  └─ 在 parent.subtasks 里按标题找 item.task
       ├─ 找到 → 直接用它
       └─ 找不到 → getCreateMeta('10003') 后 createIssue 新建子任务
```

问题：

1. 用户无法阻止创建（例如子任务标题与工时类型名不一致、或该项目不允许随手建子任务）。
2. 用户无法指定一个**已存在但标题不同**的子任务（例如实际子任务叫「支付链路改造」，而工时类型只映射到「需求调研及分析」）。
3. 子任务创建失败会让整条工时失败（`requireFields`/权限/字段配置），而用户本来只是想挂到已有子任务上。

### 3.2 目标交互

- **默认**：沿用自动匹配 → 找不到则自动创建（零行为变化）。
- **可选**：用户为某条记录指定一个已存在的子任务，提交时**直接使用，不再创建**。
- 指定方式：从当前工单的子任务列表中选择，或手输子任务号（两者都最终落到子任务 key，由服务端校验归属）。

### 3.3 数据模型

记录（草稿/批次项/历史）新增三个可选字段：

```jsonc
{
  "task": "需求调研及分析",        // 既有：工时类型映射出的分类，用于月度/需求判定
  "subtaskKey": "EXEPD-229901",  // 新增：指定的现成子任务
  "subtaskTitle": "支付链路改造",  // 新增：仅用于展示
  "createSubtask": false          // 新增：false 表示不允许自动创建
}
```

语义（按优先级）：

| subtaskKey | createSubtask | 行为 |
| --- | --- | --- |
| 有值 | 任意 | 使用该子任务；若找不到直接报错，**不创建** |
| 空 | 未设置 / `true` | 现状：按标题匹配，匹配不到则创建 |
| 空 | `false` | 报错「请选择已有子任务，或允许自动创建」 |

设计上**不新增 `subtaskMode` 字段**：`subtaskKey` 有值即代表手选，`createSubtask:false` 只用于"我不想让它偷偷创建"的显式表达。字段越少，历史记录与旧版本兼容越简单。

### 3.4 校验层（[app/worklogs.js](../../app/worklogs.js) 第 62–71 行）

在现有 `task` 校验之后追加：

```js
const subtaskKey = typeof record.subtaskKey === 'string' ? record.subtaskKey.trim() : '';
if (subtaskKey && !/^[A-Z][A-Z0-9_]*-\d+$/.test(subtaskKey)) throw fieldError('subtask','请选择有效的子任务');
if (record.createSubtask === false && !subtaskKey) throw fieldError('subtask','请选择已有子任务，或允许自动创建');
```

要点：

- `task` 仍必须与工时类型匹配（分类语义不变），手选子任务**不改变分类**，只改变"工时挂到哪个子任务"。
- `subtaskKey` 只做格式校验；**归属校验必须放在服务端**（页面拿到的列表可能过期）。

### 3.5 提交解析（[app/submission.js](../../app/submission.js) 第 222–246 行）

**已确认：手填子任务优先（以手填为准）。** 这改变了原有"先定父工单、再找/建子任务"的顺序——手填时必须**先解析子任务，再由它反推父工单**，否则会出现"父单已经创建/选定，用户手填的却是另一个父单下的子任务"。

```js
// 1) 手填优先：先按 key 取子任务，父工单由它反推
if (item.subtaskKey) {
  const target = await this.jira.getIssue(item.subtaskKey);
  if (target.typeId !== '10003') throw jiraError('SUBTASK','该编号不是子任务。');
  const parent = await this.jira.getIssue(target.parent);   // 反推父单
  if (parent.project !== batch.scope.project) throw jiraError('SUBTASK','该子任务不在当前项目中。');

  // 2) 用父单校验任务类型：需求任务→故事(10001)；月度任务→综合工时单(10002)
  if (monthlyTasks.includes(item.task)) validateMonthly(parent, batch.scope, this.jira.identity);
  else if (parent.typeId !== '10001') throw jiraError('SUBTASK','该子任务不属于需求故事，无法挂需求类工时。');

  // 3) 手填为准：覆盖原工单；月度父单顺手绑定该月，后续行与月视图保持一致
  item.issue = parent.key; item.issueTitle = parent.title;
  if (monthlyTasks.includes(item.task)) await this.bindMonth(batch, item.day, parent, '手选子任务');
  item.targetId = target.id; item.targetKey = target.key; item.targetTitle = target.title;
  item.phase = 'ready'; await this.persist(batch);
  return;
}

// 4) 未手填：维持现状——解析父单后按标题匹配，匹配不到才创建
```

要点：

- **不创建**：手填分支里没有任何 `createIssue` 调用，即使子任务列表里找不到该 key 也不会新建。
- **父单以子任务为准**：原来已选的需求故事、或自动匹配到的月度父单，都会被手填子任务的真实父单覆盖；批次项记录 `issueSource:'subtask'`，便于排查"为什么挂到了这个工单"。
- **月度绑定**：若反推出的父单是当月综合工时单，写入该月 binding（`source:'手选子任务'`），避免后续行又创建一张月度单。
- 反查用 `getIssue(key)` 两次（子任务 + 父单），提交前一次性完成；失败不产生任何写入。
- `reconcile` 只用 `targetKey + 时间 + 说明` 判重，手选不影响核对逻辑。

配套：

- [app/jira.js](../../app/jira.js) 第 154 行 `normalizeIssue` 的子任务目前只有 `id/key/title/typeId`。**已确认允许选择已关闭/已完成的子任务**，因此本次把子任务状态一并取回：
  ```js
  subtasks:(f.subtasks||[]).map(item=>({
    id:String(item.id), key:item.key,
    title:item.fields?.summary||'',
    typeId:item.fields?.issuetype?.id,
    status:item.fields?.status?.name||'',
    statusCategory:item.fields?.status?.statusCategory?.key||''  // new | indeterminate | done
  }))
  ```
  列表里对 `statusCategory==='done'` 的项显示「已完成/已关闭」灰标，但**不禁用**；是否可写工时由 Jira 权限决定，提交失败按现有 `400 → FIELDS` 文案提示。
- 子任务创建成功后仍然写回 `targetId/targetKey`，重试时不再重复创建（现状已如此）。

### 3.6 界面

> **已确认的两条范围**：批量填报必须能**手填**子任务；月度综合工时单同样必须能**手填**子任务（不要求先在日填报里绑定月度工单）。

#### 3.6.1 日填报（[app/ui/renderer.js](../../app/ui/renderer.js) 第 203–221 行 `renderTask`）

现状：子任务区域只有一排 chip，展示「已创建 / 未创建 · 提交时自动创建」，且只有自动匹配项可点。

改为：

1. 已有工单被选中且该工单有子任务时，chip 下方增加一行：
   ```
   子任务：[自动匹配或创建「需求调研及分析」▾]
   选项：自动（默认）/ EXEPD-229901 · 支付链路改造 / EXEPD-229902 · 埋点补充（已完成）
   ```
2. 选择具体子任务后，chip 区显示「已选：支付链路改造（EXEPD-229901）」，并在提交记录里写入 `subtaskKey/subtaskTitle/createSubtask:false`。
3. **月度工单**（`monthlyTasks` 命中，`issueSelection` 为空、拿不到父工单子任务）时，固定展示手输框：
   ```
   已有子任务号 [ EXEPD-229903 ] （留空则自动匹配或创建「日常综合」）
   ```
   不要求先绑定月度工单；提交时由服务端回查该子任务的父工单是否就是当月的综合工时单。
4. 已关闭/已完成的子任务照常出现在列表里，仅加灰标，不阻断选择。
5. 校验失败时 `field:'subtask'` 映射到该控件并聚焦。

#### 3.6.2 批量填报（本次改造的核心落点）

##### 现状链路（决定了要补哪些口子）

| 环节 | 代码 | 现状 |
| --- | --- | --- |
| 表格生成 | [app/ui/renderer.js](../../app/ui/renderer.js) 第 557–617 行 `renderBatchRows` | 第 7 列是 `<span data-task>` **只读文本**（第 566 行） |
| 工单选择 | 同文件第 605–607 行 `issueSearch` 的 `chosen` 回调 | 拿到 `detail`（含 `subtasks`），但**只用了 key/title/task，没有保存子任务列表** |
| 数据持久化 | 同文件第 567 行 `save()` → `saveDraft` | 整行 spread 保存，所以新增字段会**自动落盘**，无需改存储层 |
| 校验 | 第 558 行 `agentNotice`、第 568–578 行 `markMissing`、第 621/629 行 `reviewBatch` | 三处都只看标题/日期/工时/类型/工单，**没有子任务维度** |
| 提交前过滤 | 第 649 行附近 `submitRecords` 用 `validateRecord` 过滤 | 不合法行被排除并提示"请先补齐待提交事项" |
| 待办带入的行 | `importTodos` 产出记录 | `issue` 可能已从标题解析，但**没有 `subtasks` 列表** |
| 从批次返回草稿 | [app/submission.js](../../app/submission.js) 第 84 行 `returnToDrafts` | 会剥掉 `targetId/targetKey`，但保留 `subtaskKey` |

结论：批量页必须补 **数据字段、取数方式、单元格交互、四处校验** 这四件事，只改日填报是不够的。

##### 3.6.2.1 数据与状态

- `row.subtaskKey` / `row.subtaskTitle`：**随行持久化**到草稿（`saveDraft` 整行保存，天然生效）。
- 子任务列表**不持久化**：JIRA 侧随时会新增/关闭子任务。用页面级内存缓存：
  ```js
  const subtaskCache = new Map(); // issueKey -> {items, error?, at}
  ```
- 行级仅内存状态：`row.subtaskOptions`、`row.subtaskLoading`，不写入草稿（避免把过期列表写进存档）。

**清空规则**（已按"手填为准"调整：手填项不再被工单变更连带清空）：

| 操作 | subtaskKey / subtaskTitle |
| --- | --- |
| 清空子任务输入 | 清空（回到工单自动匹配） |
| 重新选择工单，且子任务已手填 | **保留**，行内提示"提交以子任务所属工单为准" |
| 重新选择工单，且子任务为空 | 无影响 |
| 改工时类型导致"月度 ↔ 需求"父工单变化 | 行内提示类型与子任务父单需匹配；提交时校验，不匹配报 `SUBTASK` |
| 切换导入来源后重新解析 | 按记录 id 合并，已有草稿保留 |

##### 3.6.2.2 取数：懒加载 + 去重

- **不在渲染时批量拉取**。聚焦某行子任务输入框时才 `call('getIssue',{key: row.issue})`，用于填充候选与标题提示；没有工单或月度行则跳过。
- 同一工单只请求一次，成功后写 `subtaskCache`；失败也写缓存并允许继续手输，避免反复打网络。
- 选择工单时 `issueSearch` 的 `chosen` 已带 `detail.subtasks`，**直接写入缓存**。
- 待办带入的行：`issue` 已知 → 聚焦时懒加载候选。
- 子任务父单不预取：手填 key 后只做格式校验与"未知编号"提示，父单归属留到提交时由服务端反查（§3.5）。

##### 3.6.2.3 单元格交互（表格内直接手填）

**已确认：批量页直接在表格里增加"已有子任务"列，手填工单号**，不采用浮层选择。

表格从 7 列扩为 **8 列**（[app/ui/renderer.js](../../app/ui/renderer.js) 第 566 行的 `innerHTML`、第 563 行的 `colspan`、[app/ui/templates.js](../../app/ui/templates.js) 的列头/列宽都要改）：

```
序号 | 工作事项 | 日期 | 工时/h | 工时类型 | 关联工单 | 子任务(分类) | 已有子任务
 01  | …        | …    | 2.5   | 需求分析 | EXEPD-…  | 需求调研及分析 | [ EXEPD-229901 ]
                                                          支付链路改造 · 已完成
```

列宽建议：`4 / 19 / 13 / 8 / 12 / 17 / 12 / 15`（合计 100），表格 `min-width` 由 990px 提到 **1120px**。

规则：

- 新列是普通文本输入，`placeholder="子任务号，如 EXEPD-229901"`；留空 = 走原有"自动匹配或创建"。
- `onchange` 时写 `row.subtaskKey = 值.trim()`，随整行 `saveDraft` 落盘；清空输入即删除该字段。
- 输入合法 key 后，单元格下方用缓存/回查结果补一行灰字标题（`支付链路改造 · 已完成`）；查不到就显示"提交时校验"。
- **手填优先**：该列有值时，提交阶段以子任务所属工单为准，关联工单列的值会被覆盖。行内提示小字："提交以子任务所属工单为准"。
- **月度行**：关联工单列仍是只读的"对应月份综合工时单"，但本列照常可填；提交时反推父单并校验是否当月的综合工时单。
- **需求行未选工单**：本列仍可填；填了就能提交（父单由子任务反推），不填则提示"先选择工单"。
- 已关闭/已完成的子任务可以填：反查后照常使用，仅标题提示里带"已完成"。
- 格式非法（不是 `KEY-数字`）→ 红框 + "子任务号格式不正确"，阻止进入下一步。
- **月度工单行**同样有手输框：该行工单是只读的"对应月份综合工时单"，列表通常拿不到候选，手输是主要入口；父工单在提交时才解析，归属由服务端校验。
- 未选工单的**需求行**：按钮禁用并提示"先选择工单"（月度行不受此限制）。
- 已关闭/已完成的子任务显示灰标但可选。
- 表格列头（[app/ui/templates.js](../../app/ui/templates.js) 批量模板）：第 7 列由「子任务 AI建议」改为「子任务」；**新增第 8 列「已有子任务」**（附小字"可手填"）。

##### 3.6.2.4 校验与提示（四处都要改）

1. `markMissing`（第 568–578 行）新增：
   - `subtaskKey` 非空且格式不合法 → `invalid`，提示"子任务号格式不正确"
   - `subtaskKey` 不在缓存列表中 → 不算错，加"提交时校验"小字

### 3.7 边界与异常

| 场景 | 处理 |
| --- | --- |
| 手选的子任务已被删除/不可见 | 提交时报 `SUBTASK`，不创建、不写工时，提示重新填写 |
| 手填的是父工单本身或非子任务类型 | 反查校验 `typeId==='10003'`，不符即拒绝 |
| 子任务属于其他项目 | 反查父单后校验 `project === batch.scope.project`，不符即拒绝 |
| 子任务已关闭/已完成 | **已确认允许选择**：界面显示灰标但不禁用；写入工时的可行性由 Jira 权限决定，失败按现有 `400 → FIELDS` 提示。需要 [app/jira.js](../../app/jira.js) 的 `normalizeIssue` 额外返回子任务状态 |
| 月度工单尚未绑定 | **以手填为准**：由子任务反推父单，若为当月综合工时单则顺手绑定该月；未手填时才走原有的匹配/创建 |
| 手填子任务的父单与行内已选工单不一致 | **以手填为准**，覆盖为子任务父单；行内提示"提交以子任务所属工单为准" |
| 重试 | `subtaskKey` 随批次项持久化，重试不再触发创建 |
| 旧草稿 | 无新字段 → 走默认自动逻辑，行为不变 |
| **批量**：行先填子任务、后换工单 | 手填优先，`subtaskKey` 保留并提示以子任务父单为准；要按工单走需手动清空该列 |
| **批量**：候选/标题提示请求失败 | 只影响灰字提示，不影响手输与提交 |
| **批量**：子任务被 Jira 删除但本地草稿仍记着 | 提交时反查失败 → `SUBTASK`，提示返回填报修正；草稿保留便于改 |
| **批量**：月度行 + 手填子任务 | 以子任务父单为准并绑定该月，不新建月度单 |
| **批量**：一次带入 20 条来自不同工单的待办 | 只在该行输入框聚焦时取该工单候选，按工单去重；不做 N 条并发预取 |

### 3.8 备选方案比较

| 方案 | 交互成本 | 正确性 | 结论 |
| --- | --- | --- | --- |
| **A. 表格内直接手填子任务号（已确认）** | 最低，一行一填 | 服务端反查父单，最稳 | 采用 |
| B. 浮层里选已有子任务 + 手输 | 中，多一次点击 | 同上 | 不采用（用户明确要求表格内直接填） |
| C. 只允许浮层选择，不能手输 | 低 | 列表不全时无法处理 | 不采用 |
| D. 提交失败后弹窗再选 | 中 | 流程割裂，失败已产生一次远端请求 | 不采用 |

## 5. 测试计划

### 5.1 粒度

- `0.25` 合法且 `seconds===900`；`0.1`、`0.375`、`0`、`''` 非法。
- 快捷块含 9 个值（含 `0.75`、`1.25`），点击后输入框同步；日填报两行排布不挤压输入框。
- 待办完成对话框可选 0.25/0.75/1.25；批量兜底耗时接受 0.25；历史编辑接受 0.25。
- 批量页缺失提示文案为「0.25h倍数」。
- 汇总：`0.25+0.5+1.25 = 2`（验证无浮点尾差）。

### 5.2 子任务

- 手填子任务 → 提交只调用工时接口，**不调用** `getCreateMeta('10003')` / `createIssue`。
- **父单反推**：手填 `EXEPD-229901`（其父为 `EXEPD-229900`），即使行内 `issue` 填的是另一个工单，最终工时也写到 `EXEPD-229901`，父单被覆盖为 `EXEPD-229900`。
- 手填的是需求故事或普通任务（`typeId !== '10003'`）→ `SUBTASK`，无写入。
- 子任务属于其他项目 → `SUBTASK`，无写入。
- `createSubtask:false` 且未填子任务 → 校验期即拒绝（`INVALID_RECORD`，field=`subtask`）；批量页不会产生该状态（留空=自动）。
- 默认路径回归：未填且找不到 → 仍然自动创建（现有 `TC-013` 用例保持通过）。
- **月度工单 + 手填子任务**：父单由子任务反推，若为当月综合工时单则写入该月 binding（`source:'手选子任务'`）；不匹配当月/不是 10002 类型 → `SUBTASK`。
- **已关闭/已完成的子任务**：可见可选可提交；能否写入由 Jira 权限决定，失败信息可读。
- 手填后清空输入 → 回到"按工单自动匹配/创建"。

## 6. 风险与回滚

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 三处校验器漏改其一 | 某入口仍拒绝 0.25 | 常量集中 + 用例覆盖三条路径 |
| 界面仍限制 `step=0.5` | 用户输 0.25 被浏览器拦截 | §4 列出全部 7 处控件，逐处核对 |
| 手选子任务绕过类型分类 | 报表口径混乱 | `task` 分类保持不变，仅 `targetKey` 变化；历史同时展示两者 |
| 子任务列表过期 | 提交失败 | 服务端回查 key 校验归属，而不是信任页面 |
| 旧草稿/旧批次无新字段 | 行为变化 | 全部字段可选，缺省即旧逻辑 |

回滚成本低：粒度改的是常量与控件；子任务是**新增可选字段 + 一个 if 分支**，回退只需删除分支与字段读取。

## 7. 验收标准

1. 日填报、批量、待办完成、历史编辑四个入口都能录入 0.25h，且提示文案一致。
2. 0.125h、0.3h 等仍被拒绝，错误信息指向工时字段。
3. 不填子任务号时，行为与现在完全一致（自动匹配→创建）。
4. 填了子任务号时，JIRA 侧工时挂在**该子任务**下，且不新建任何子任务。
5. 填了子任务号时，**父工单以子任务为准**：即使行内选的是另一个工单，最终也写到子任务的父单，并在结果中可追溯。
6. 子任务号不存在/不是子任务/不在当前项目/父单类型不匹配时，提交前或提交时给出明确错误，且不产生任何远端写入。
7. 现有 165 项通过用例保持通过（7 项 Windows 环境限制除外）。
8. **批量填报**：第 2 步表格为 8 列，新增"已有子任务"列可直接手填；`saveDraft` 草稿含 `subtaskKey`，刷新/重进页面回显。
9. **批量填报**：清空该列即可回到"自动创建"；换工单不会清掉手填值，并提示"提交以子任务所属工单为准"。
10. **批量填报**：不填子任务号的行，行为与改造前完全一致，不影响现有批量流程。
11. **月度综合**：日填报与批量页都能手填子任务号，无需先绑定月度工单；父单由子任务反推并绑定该月。
12. **已关闭子任务**：可见、可填、可提交；若 Jira 拒绝，错误信息可读。
