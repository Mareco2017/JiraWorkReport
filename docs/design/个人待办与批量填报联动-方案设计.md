# 个人待办 × 批量填报 联动方案设计

- 文档状态：**已实施（2026-11-16），见第 13 节实施记录**
- 日期：2026-11-16
- 范围：个人待办「完成时记录工时」+ 批量填报「从已完成待办带入」
- 目标版本：0.2.0

---

## 1. 背景与目标

### 1.1 用户诉求

1. 个人待办点「完成」时，允许补充填写本次投入的工时。
2. 批量填报增加一种内容来源：**从已完成待办带入并解析**，直接生成工时记录。

### 1.2 现在为什么不联动

| 环节 | 现状 | 结果 |
| --- | --- | --- |
| 待办数据 | `personal-todos.json` 只有标题/说明/截止/优先级/分组/状态/评论（[app/todo-data.js](../../app/todo-data.js) 第 26、46 行） | **没有任何工时字段** |
| 完成动作 | `todoSetStatus` 只写状态与 `updatedAt`（[app/todos.js](../../app/todos.js) 第 65 行） | 完成时**没有输入工时的地方** |
| 批量带入 | 已存在 `importTodos`（[app/batch-import.js](../../app/batch-import.js) 第 58–80 行），但所有行统一取页面上的"默认耗时/类型" | 多条待办**时长全都一样**，日期取 `updatedAt`（评论也会刷新它），并非完成日期 |
| 回写 | 无 | 提交成功后待办侧**没有任何痕迹**，无法区分"已带入/已登记" |

> 说明：`importTodos` 是上一轮赶工留下的半成品，本方案需要重构它，而不是在它之上叠加。

### 1.3 设计目标

- **单一事实来源**：工时由待办记录一次，批量页只做"带入 + 补齐 + 提交"，不产生第二份需要人工同步的工时。
- **不强制、可跳过**：完成时可以不填，之后在详情页或批量页补。
- **不依赖模型**：带入主路径纯本地映射；AI 只用于"类型建议"，且失败即降级。
- **幂等**：同一条待办最多生成一条记录、最多登记一次。

### 1.4 非目标

- 不在待办侧直接提交 JIRA 工时（提交仍然只发生在批量页/填报页）。
- 不做团队共享待办（仍为本机数据）。
- 不改变现有"工时必须是 0.5 倍数"的规则。

---

## 2. 总体设计

一条单向流水线，三个动作各自职责清晰：

```
待办完成（记录工时）
      │  workLog{hours,type,issue,day,note}
      ▼
批量填报·已完成待办页签（带入 + 可选 AI 建议类型）
      │  draft(record)  ── 与按天/文档/粘贴完全同构
      ▼
提交（既有 SubmissionService 逐条写入）
      │  成功 → history + 回写 todo.workLog.state='submitted'
      ▼
待办详情显示「已登记 2h · 工单 EXEPD-xxxxx」
```

关键原则：

1. **待办只记录，不提交**；提交仍走既有链路，失败/重试/删除语义不变。
2. **draft 是提交前的工作副本**：带入后允许改工时/类型/工单，改动不回写待办（避免双向同步的冲突），但提交结果回写。
3. **身份稳定**：记录 id 由待办 id 派生，重复带入、重复提交都能被现有机制识别。

## 3. 数据模型

### 3.1 待办新增字段

```jsonc
{
  "id": "dd1dc1bb-…",
  "title": "EXEPD-205297 作业增加AI批阅功能",
  "status": "已完成",              // 既有
  "updatedAt": "2026-11-16T02:11:03.000Z",   // 既有：任意修改都会变
  "completedAt": "2026-11-16T02:11:03.000Z", // 新增：首次转为已完成的时间
  "workLog": {                     // 新增：可为 null（老数据/未填写）
    "hours": 2,
    "day": "2026-11-16",           // 默认完成当天，可改
    "type": "需求分析",             // 可空
    "issue": "EXEPD-205297",       // 可空，默认从标题解析
    "issueTitle": "",
    "note": "",                    // 为空时用标题作为工时备注
    "state": "recorded"            // recorded | submitted
  }
}
```

字段取舍说明：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 完成时间 | 新增 `completedAt`，**不复用 `updatedAt`** | `updatedAt` 会被评论、改标题刷新，作为工作日期是错误的 |
| 工时结构 | 嵌套对象 `workLog` | 与"状态"解耦：可以先完成、后补工时 |
| 是否必填 | `workLog` 可缺省 | 兼容老数据；不阻塞"只想打卡完成"的用户 |
| 状态枚举 | `recorded` / `submitted` | 只区分"记了"和"已登记"；提交失败仍是 `recorded` |

### 3.2 校验规则（在写入边界执行）

- `hours`：数字、≥0.5、是 0.5 的倍数（与 [app/worklogs.js](../../app/worklogs.js) 第 56 行一致）。
- `day`：`YYYY-MM-DD`，且不晚于今天。
- `type`：非空字符串时可保存；**是否有效以 JIRA 返回的类型清单为准**，在带入/提交时校验。
- `issue`：可空；非空时须匹配 `^[A-Z][A-Z0-9_]*-\d+$`。
- `note`：字符串，长度上限 500（与工时备注一致）。
- 任何一项非法 → 抛 `TODO_VALIDATION`，**不落盘**（保持现有"失败不改文件"的约定，见 `tests/todos.test.js` 第 44–51 行）。

### 3.3 兼容与迁移

- 读取：`workLog` 缺失视为 `null`；`completedAt` 缺失时回退到 `updatedAt`（仅用于显示，不回写）。
- 校验：[app/todo-data.js](../../app/todo-data.js) 第 44–51 行的 `validateTodoState` 必须**允许缺省**新字段；`workLog` 存在时逐字段校验。
- 写入：只在用户首次保存工时时补 `completedAt`/`workLog`，不批量重写历史文件。

## 4. 交互设计

### 4.1 完成待办时填写工时

**触发入口（四个都必须走同一套逻辑）**

1. 列表行左侧勾选框勾选（[app/ui/todo/view.js](../../app/ui/todo/view.js) 第 419–423 行）
2. 详情底部「完成待办」按钮（同文件第 571–574 行）
3. 详情「状态」下拉切到"已完成"（同文件第 553–555 行）
4. 日历视图里的已完成标记（走 2/3 即可）

**对话框内容**（动态创建 `<dialog>`，参照 `confirmDeleteRecord` 的做法）

```
┌ 记录本次工时 ──────────────────────────┐
│ 待办：EXEPD-205297 作业增加AI批阅功能    │
│                                       │
│ 工时 *      [0.5][1][1.5][2][2.5][3]  │
│             [ 自定义 ____ ] h          │
│ 工作日期    [ 2026-11-16 ▾ ]           │
│ 工时类型    [ 需求分析 ▾ ]（记住上次）  │
│ 关联工单    [ EXEPD-205297 ]（自动解析）│
│ 备注        [ 默认同标题            ]   │
│                                       │
│ [取消]      [暂不填写，仅完成] [保存并完成] │
└───────────────────────────────────────┘
```

**默认值规则**

| 字段 | 默认 |
| --- | --- |
| 工时 | 空（必须用户选/填；不猜） |
| 日期 | 今天 |
| 类型 | 该账号最近一次使用过的类型（存于配置 `commonTypes[0]` 或新增 `lastWorkType`） |
| 工单 | 从标题中解析当前项目的 `KEY-数字`；解析不到则空 |
| 备注 | 空（提交时回落为标题） |

**"暂不填写，仅完成"** 的后果：`status='已完成'`、`workLog=null`、`completedAt=now`。此类待办会在批量页显示为"待补工时"，不能直接带入。

**取消**：状态不改变，勾选框回滚（复用现有 `changeStatus` 的回滚模式）。

### 4.2 详情页补填 / 修改

- 详情字段区新增一行「工时」：已填显示 `2 h · 需求分析 · EXEPD-205297`，未填显示"未填写"。
- 点击 → 打开同一个对话框（预填现有值），保存走 `todoSetWorklog`，**不改变状态**。
- 已 `submitted` 的工时：对话框改为只读并提示"已在 JIRA 登记，如需修改请到填报记录中编辑"，避免本地与远端不一致。

### 4.3 取消完成

- 用户把状态改回"待处理/进行中"：保留 `workLog` 与 `completedAt`（不清空，避免误操作丢数据），仅状态变化。
- 若该待办已 `submitted`：先提示"该待办工时已登记，回退状态不会删除 JIRA 工时"，确认后仅改状态。

### 4.4 批量填报：第三个页签「已完成待办」

**布局**（沿用现有左列表 + 右说明的两栏版式）

```
┌ 已完成待办 ────────────────────────────────┐
│ 已选 3 条 · 合计 5.5 h     [显示已登记] [刷新]│
├────────────────────┬───────────────────────┤
│ ☑ 11月16日 · 2.0h   │  带入规则              │
│   EXEPD-205297 …    │  · 时长/类型/工单取自   │
│   需求分析           │    待办记录            │
│ ☑ 11月15日 · 1.5h   │  · 日期取完成当天       │
│   jira工时填报-测试  │  · 未填类型的可选择让   │
│   待补类型           │    AI 建议（可选）      │
│ ☐ 11月14日 · 已登记  │  · 已登记的不会再次带入 │
│   2h · 需求评审      │                       │
└────────────────────┴───────────────────────┘
                        [带入并解析]
```

**列表规则**

- 默认只列 `status='已完成'` 且 `workLog.state!=='submitted'` 的待办。
- 按 `completedAt` 倒序分组显示（今天 / 昨天 / 11月14日）。
- 行内显示：标题、时长（或"待补工时"）、类型（或"待补类型"）、工单号、"已登记"徽标。
- 无工时的行可勾选，但带入时该行 `hours` 留空并标记缺失，在第 2 步补。
- 「显示已登记」开关用于查阅，勾选时禁止选择。

**带入动作**

1. 读取选中待办的 `workLog`，逐条映射为记录（见 §6.1 映射表）。
2. 对 `type` 为空的记录：若 Agent 已配置且去向已核实 → 调用一次批量类型建议（复用 `AgentService.suggest`，入参 `{id,title}`）；否则跳过。
3. 与现有 draft 合并（`mergeDrafts`），已提交过的记录自动排除。
4. 进入现有第 2 步表格，用户可逐条修改后提交。

**默认值区保留但降级**：仅对"待办未填工时/类型"的行生效，且默认值从"所有行统一"改为"缺失行兜底"，避免覆盖待办里已记录的时长。

## 5. 流程与状态机

### 5.1 待办工时状态

| 状态 | 含义 | 进入条件 | 出口 |
| --- | --- | --- | --- |
| `null` | 未记录工时 | 完成时选择"暂不填写"/老数据 | 补填 |
| `recorded` | 已记录，未登记 | 完成时填写，或详情补填 | 带入、提交成功、删除草稿 |
| `submitted` | 已登记到 JIRA | 提交成功回写 | 删除填报记录后回退 |

```
完成 ──填写──▶ recorded ──带入──▶ draft ──提交成功──▶ submitted
  │                              │
  └─暂不填─▶ null ──补填──▶ recorded └─删除草稿─▶ recorded
```

### 5.2 幂等与去重

| 场景 | 机制 |
| --- | --- |
| 同一条待办重复带入 | 记录 `id = sha256('todo\n'+todoId).slice(0,24)` 固定，`mergeDrafts` 已存在则跳过 |
| 已提交后再次带入 | `result()` 依据 `history` 中同 id 的 success 记录返回 `registered`，不再生成草稿 |
| 同一批重复点击"带入" | 导入前先 `clearReadFeedback` + 选择集清空，按钮在忙碌时禁用 |
| 删除草稿后重新带入 | draft 被移除，记录重新生成，`workLog.state` 仍为 `recorded` |

### 5.3 源标识设计（修正现有实现的缺陷）

现有实现把"本次选中集合"的哈希同时用作 `source.id` 与每条记录的 `importSourceId`，导致：

- 换个选择集再带入，同一待办的 `importSourceId` 会变；
- 切回页签时用 `drafts.filter(importSourceId===source.id)` 恢复，会漏掉或串入别的待办。

**改为**：

| 标识 | 取值 | 用途 |
| --- | --- | --- |
| 记录 `importSourceId` | `'todo:'+todo.id`（每条固定） | 草稿来源过滤、恢复编辑 |
| 页签 `source` | `{id:'todo', kind:'todo', name:'已完成待办', contentHash:hash(选中id排序)}` | 只用于展示与"本次预览"标识 |
| 提交批次键 | 沿用 `batch/<source.id>`，即 `batch/todo` | "查看本次提交"入口 |

## 6. 接口与实现设计

### 6.1 待办 → 记录 映射

| 记录字段 | 来源 | 缺省处理 |
| --- | --- | --- |
| `id` | `sha256('todo\n'+todo.id)` 前 24 位 | — |
| `todoId` | `todo.id` | — |
| `title` | `todo.title` | 空标题不允许（待办创建时已校验） |
| `hours` | `workLog.hours` | 空 → 页面兜底默认值；仍空则标缺失 |
| `day` | `workLog.day` | 空 → `completedAt` 当天；再空 → 缺失 |
| `type` / `task` | `workLog.type` → `typeMapping` | 空 → AI 建议或手选；task 由 type 推导 |
| `issue` | `workLog.issue`，否则从标题解析 | 空 → 由月度工单规则决定 |
| `note` | `workLog.note`，否则 `title` | — |
| `source` | `'批量填报'` | — |
| `sourceKind` | `'todo'` | — |

### 6.2 命令（IPC 白名单见 [app/service.js](../../app/service.js) 第 36 行）

| 命令 | 入参 | 校验 | 副作用 |
| --- | --- | --- | --- |
| `todoComplete` | `{id, workLog?}` | 状态存在、workLog 合法 | 状态→已完成，写 `completedAt`，`workLog.state='recorded'` |
| `todoSetWorklog` | `{id, workLog}` | 同上；已 `submitted` 时拒绝 | 仅更新工时，不改状态 |
| `importTodos` | `{ids, fallback?:{hours,type}, useAgent?:boolean}` | 非空、去重、全部为已完成 | 生成/合并草稿，返回记录与警告 |

> `todoComplete` 与 `todoSetWorklog` 的字段解析**必须复用同一套校验**，且放在 `parseCommand`（[app/todos.js](../../app/todos.js) 第 7–23 行）里，避免页面传入 `status`/`createdAt` 等越权字段。

### 6.3 提交回写

- `SubmissionService` 构造参数新增 `onItemSettled(item, batch)` 回调，在 [app/submission.js](../../app/submission.js) 第 196 行 `accept` 之后触发。
- `WorkbenchService` 注入：成功且 `item.todoId` → `personalTodos.markSubmitted(todoId, {worklogId, day})`；失败/不确定 → 不动（保持 `recorded`）。
- 删除填报记录时（[app/submission.js](../../app/submission.js) 第 97–111 行 `deleteRecord`）→ 若记录带 `todoId`，把对应待办回退为 `recorded` 并清空 `worklogId`。
- 回写必须是**幂等**的：重复调用只覆盖同样的值；待办已被删除则静默跳过。

## 7. 边界与异常

| 场景 | 处理 |
| --- | --- |
| 完成时跳过填写 | 允许；批量页显示"待补工时"，带入后需手补 |
| 待办工时类型已失效（站点调整） | 带入时用 live types 校验，失效行标红要求重选，不静默改类型 |
| 待办标题无工单号且类型是月度类 | 按现有月度工单规则自动落到综合工时单（`monthlyTasks`） |
| 跨月带入（10月完成、11月提交） | 日期以 `workLog.day` 为准；月度工单按该日期所在月解析 |
| 同一天多条待办、合计超过 7.5h | 不阻止（与按天填报一致），仅在合计处提示 |
| 已提交待办被再次勾选 | 列表禁用选择 + 文案说明"已登记" |
| 删除待办但工时已登记 | 只删本地待办，历史与 JIRA 工时保留；提示用户 |
| 待办在带入后被删除 | 草稿仍在（记录自带标题/工时），提交不受影响；回写时找不到待办则跳过 |
| 切换账号/项目 | 待办不分账号；带入时按当前项目解析工单号，已带工单号的行校验归属 |
| 文件损坏 | 沿用现有 `TODO_READ_FAILED`，不覆盖原文件 |

| `importTodos` 映射 | 时长/类型/工单/日期逐字段来自待办，而非页面默认值 |
| 缺失兜底 | 待办无工时时用 fallback；fallback 也空则 `missing` 含 `hours` |
| 去重 | 同 id 二次带入不新增草稿；已提交返回 `registered` |
| 类型建议 | Agent 可用时补齐类型；不可用/超时 → 保留空并给警告，不影响带入 |
| 回写 | 提交成功 → `state='submitted'` + `worklogId`；删除记录 → 回退 `recorded` |

### 8.2 UI（Electron 宿主）

- 勾选完成 → 出现对话框；保存 → 行状态与徽标更新、待办详情出现工时。
- "暂不填写" → 状态已完成、无工时。
- 取消 → 状态与勾选回滚。
- 批量页：列表只显示未登记；勾选 2 条带入 → 第 2 步出现 2 行且时长各不相同；提交后返回列表显示"已登记"。

> 现有 `todo-ui.test.js` / `batch-ui.test.js` 在本机 Electron 子进程不退出，需先修复测试宿主再纳入门禁（见 §10）。

## 9. 风险与取舍

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 两处工时不一致（待办记录 vs 草稿修改） | 用户困惑"到底哪个算" | 明确单向：草稿可改、不回写；提交后以 JIRA 为准，待办只显示登记结果 |
| `importTodos` 重写 | 已发布的半成品行为变化 | 新实现仍接受旧的 `{ids,hours,type}` 调用，作为 fallback 分支 |
| 完成对话框打断流程 | 勾选完成变慢 | 提供"暂不填写"一键跳过；对话框记住上次类型 |
| AI 建议依赖模型去向核实 | 与上一轮 `DESTINATION_UNVERIFIED` 同类问题 | AI 为可选增强；未核实时直接跳过并提示"可手动选择类型" |
| 待办文件结构变化 | 老版本回退读取失败 | 新字段全部可选；旧版读取时忽略未知字段（现状即如此） |
| 日历/列表/详情三处入口不一致 | 漏触发对话框 | 统一收敛到 `completeTodo(todo)` 一个函数 |

## 11. 验收标准

1. 完成待办时可填工时（0.5 倍数），可跳过；四条入口行为一致。
2. 详情页可补填/修改；已登记后只读并引导到填报记录。
3. 批量页「已完成待办」列出的每条时长来自各自待办，不再"全部同一个值"。
4. 已登记的待办不出现在可带入列表；重复带入不产生重复记录。
5. 提交成功后待办显示"已登记 + 工时 + 工单"；删除填报记录后回退为"已记录"。
6. 未配置/未核实模型时，带入与提交完全可用（不依赖 AI）。
7. 新增/变更用例全部通过，且不破坏现有 151 项通过用例。

## 12. 待确认问题（需产品决策）

1. **完成时是否强制填工时？** 本设计选择"可跳过"。若要求强制，需明确"不填不许完成"是否会让快速打卡变难受。
2. **类型是否在待办侧必填？** 本设计选择"可空 + 批量页补齐/AI 建议"。
3. **待办删除已登记工时**：只删待办（保留 JIRA 工时），还是同时删除工时？本设计选前者。
4. **历史待办**（已完成但无工时，如现有 4 条中的 1 条）：是否需要在待办页批量"补录"入口？本设计暂不做，靠批量页兜底。

### 13.2 关键实现点

- **命令**：新增 `todoComplete`、`todoSetWorklog`（[app/todos.js](../../app/todos.js)），字段解析统一走 `todoWorkLog`（[app/todo-data.js](../../app/todo-data.js)），页面无法越权写 `status`/`createdAt`。
- **记录身份**：记录 `id = sha256('todo\n'+todoId)`，`importSourceId = 'todo:'+todoId`；页签 `source.id` 固定为 `todo`——修正了原实现"换选择集就换来源"的缺陷。
- **映射优先级**：工时/类型/工单/日期取待办记录，页面"兜底值"只补缺失项。
- **回写**：`SubmissionService` 新增 `onItemSettled`/`onItemRemoved` 钩子，由 `WorkbenchService` 接到待办；回写异常被吞掉，不影响已成功的远端提交。
- **AI 建议**：带入后仅对缺类型的记录调用一次 `AgentService.suggest`；`DESTINATION_UNVERIFIED` 等异常时返回提示并保留空类型。
- **批量页**：默认隐藏已登记项，可用"显示已登记的待办"查看；已登记行禁用且不参与全选（并修正了忙碌状态统一开关把它重新启用的缺陷）。

### 13.3 与设计的差异

1. 设计第 12 节的四个待确认问题均按文档默认值实施：完成可跳过、类型可空、删除待办保留 JIRA 工时、不做历史补录入口。
2. Windows 下 `chmod` 不阻止写入，`tests/todo-ui-host.cjs` 的只读失败断言改为仅在类 Unix 平台执行，其余流程在 Windows 全量跑通。
